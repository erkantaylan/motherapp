# CPU tool, read-only step (2026-10-22, sub-agent on the user's machine: CPU tool builder)

Built `tools/cpu/` (`cpuctl`, declarative page), the first step toward a Linux ClockTuner for
Ryzen. Read-only: sysfs/procfs reads only; the only file it writes is a missing
`~/.config/motherapp/cpu.json`. Ran on the machine itself (Ryzen 9 3900X), so the parsers were
checked against the real files, not memory.

## Lessons

- [local] The real 3900X sysfs, for whoever writes the SMU step: `topology/die_id` is **0 for
  every CPU**, so it can't tell the two CCDs apart; CCX comes from
  `cache/index3/shared_cpu_list` (ids 0-3), and CCD = CCX / 2 on family 0x17 (`ccxPerCcd` in
  `src/sysfs.ts`). `core_id` skips numbers (0,1,2,4,5,6,8,…: one disabled core slot per CCX),
  so rows are keyed by the lowest cpu in `thread_siblings_list`. `/sys/devices/system/cpu/cpufreq/boost`
  exists with amd-pstate-epp (there's also a per-policy `cpuN/cpufreq/boost`). Idle threads read
  1728 MHz (`amd_pstate_lowest_nonlinear_freq`), so a CCX average swings 2.5–4.2 GHz at idle;
  the per-core row shows the faster of its two threads.
- [local] hwmon on this board: k10temp = Tctl/Tccd1/Tccd2 (temp1/3/4, no temp2), asusec =
  temp1 Chipset, temp2 CPU, temp3 Motherboard, temp4 T_Sensor (-40000 when nothing is plugged
  in) and fan1 Chipset. hwmon numbers: nvme 0/1, k10temp 2, asusec 3, `asus` 4 (no inputs).
  Find chips by `name`; the fixtures shift the numbers (`hwmonOffset`) to make sure of that.
- [both] Tests inject the sysfs **root** (`readSnapshot(root)`, `MOTHERAPP_CPU_ROOT` for the
  CLI and the e2e core) and build a 3900X-shaped tree in a temp dir (`test/fixtures.ts`),
  rather than committing ~200 tiny fixture files. One test reads the real `/` and asserts only
  the shape, so it passes on any machine (cloud container included).
- [both] Requirements changed mid-build (coordinator message: exactly two profiles, `active`,
  `applyOnStart`). Keeping the profile parsing in `src/settings.ts` and the wording in
  `src/model.ts` made it a two-file change. Profiles are an object keyed by id in the file
  (fixed ids `underclock`/`overclock`), an array in memory for ordering.
- [local] Live check without touching the user's service (`/usr/bin/node core/src/main.ts`
  from this checkout, PID from `systemctl --user show motherapp -p MainPID`): a core with a
  scratch `XDG_CONFIG_HOME` whose `config.json` has `port: 7399` and every other tool disabled
  (the inbox's own listener would clash on 7324 otherwise), `XDG_STATE_HOME` scratch,
  `MOTHERAPP_RELEASE_URL=off`. Playwright from `~/.npm/_npx/6bcb61ec6d5aea22/node_modules` via
  `createRequire` took the screenshots. To stop it, match the pid by its environ
  (`tr '\0' '\n' < /proc/<pid>/environ | grep XDG_CONFIG_HOME`), not by command line: the
  service's command line differs only by an absolute path.
- [local] `npm install` (to register the new workspace) with `PATH=/usr/bin:$PATH` changed only
  the two `tool-cpu` entries in `package-lock.json`; npm printed "install scripts not yet
  covered by allowScripts" for koffi and @parcel/watcher, which is harmless here (already built).

## Open

- The user's real `~/.config/motherapp/cpu.json` doesn't exist yet: it's created on the
  service's next restart (the tool is `defaultEnabled`) or by the first `cpuctl profiles`.
  `cpuctl` lands in `~/.local/bin` only after `motherapp install` / `./install.sh`.
- The SMU step: `ryzen_smu` for Vcore/PPT/OC mode and for applying per-CCX clocks; apply the
  active profile at tool start when `applyOnStart` is true; the underclock values are unknown.
- Firefox wasn't checked (Chromium only, 1280 and 390 px wide, light and dark).
